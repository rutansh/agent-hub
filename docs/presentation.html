How we designed agent-hub: what it does, why it is built this way,
and the practices that keep AI systems safe and useful.

The problemAI help is only as consistent as the prompt

  • Every developer prompts differently, so results vary
  • Good prompts live in chats and docs, get copy-pasted, and drift
  • Big work goes straight to code: no design, one huge merge request
  • Credentials end up pasted into chat windows
What we want
  • The same proven workflow for everyone
  • Designed first, built in small reviewable pieces
  • Humans approve every visible action
  • Secrets stay on the developer's machine

The ideaTreat agent behavior like a dependency

Like npm or pip, but for the instructions that steer coding agents.

# in any project, once
apm install rutansh/agent-hub#v0.3.0

# result: same agents and skills, pinned to an exact commit
.cursor/agents/   architect  planner  builder
.agents/skills/   start-task  implement-feature  jira-tickets
                   stacked-mrs  connect-tools  ...

apm.yml

The manifest: which package and which version this project uses.

apm.lock.yaml

The lockfile: exact commit and file hashes, so everyone gets identical content.

Building blocksSkills are tasks. Agents are roles.

Skills (how to do a task)
  • start-task: entry point, asks small or epic
  • implement-feature: code a small change with repo context
  • jira-tickets: create epic and child tickets
  • stacked-mrs: ship a chain of small MRs
  • connect-tools: load credentials, check tools
Agents (who does a phase)
  • architect: interviews you, writes the design
  • planner: splits into tasks, creates Jira tickets
  • builder: implements tasks, opens stacked MRs

An agent has its own context and boundaries, and may use skills. Names are verbs for skills and role nouns for agents so they are easy to remember.

Guardrails

Epic pathDesign, plan, then build

1 architect

Reads the repo first. Interviews you in rounds of up to 4 questions: data, interfaces, security, rollout, risks. Offers options with a recommendation.

→ docs/epics/<slug>/design.md

2 planner

Splits the design into tasks that each fit one MR, ordered by dependency. You approve the list, then it creates the Jira epic and child tickets.

→ plan.md + Jira keys

3 builder

Implements each task with tests, saves each as one diff with the Jira key in the message, shows the stack, then pushes after approval.

→ stack of MRs

Agents hand work over through files, not chat memory. Each phase can be reviewed, edited and resumed.

Layers of protection
  • .env is git-ignored
  • .cursorignore keeps it out of AI context
  • Agents are told never to read, print or commit it
  • Tokens never go on a command line
  • CI fails if .env is tracked or a token has a value
  • Scoped tokens: repo; api + write_repository

Why it is built this wayKey design decisions

DecisionReason
APM for distributionManifest, lockfile and per-tool deployment already solved; no custom installer
Split into 3 agentsDesign, planning and coding need different context; smaller context, clearer boundaries
Files as hand-offsReviewable, editable, resumable; nothing lives only in chat memory
Approval gatesTickets, pushes and MRs are visible to the team, so a human says go
Fallbacks, not failuresNo Jira CLI? Tickets go to a markdown file, and the agent says nothing was created
Small tasks, stacked MRsReviewable diffs are the real bottleneck on AI-written code

Best practices for AI systems (1 of 2)Keep people in control

Approval gates

Anything visible or hard to undo (tickets, pushes, MRs, deletes) needs an explicit human go-ahead.

Verify, never trust

Treat agent output as a draft. Tests, linters, CI and code review decide, not the agent's confidence.

Least privilege

Personal, scoped, revocable tokens. No secrets in prompts or chat. Keep .env out of context.

Small scope, small blast radius

One task, one diff. Small changes are easy to review and easy to revert.

Honest reporting

The agent must say when a check did not run or a tool was missing. Never claim success it did not see.

Best practices for AI systems (2 of 2)Engineer the instructions and the context

  • Version and pin. Lockfile and tags make behavior reproducible
  • Instructions are code. PRs, CI validation, changelog
  • Explicit boundaries. Each agent lists what it will not do
  • State in files. Design, plan and status survive any chat
  • Context hygiene. Read the repo before asking. Keep agent files short
  • Supply chain. A third-party skill is a prompt that runs with your permissions: review and pin it. APM also scans for hidden Unicode
  • Data is not instructions. Text in tickets, web pages or files can carry prompt injection
  • Measure and iterate. Try on real tasks, note failures, improve the skill
